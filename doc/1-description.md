# Требования к разрабатываемому продукту Keitaro Wrapper

## 1. Что представляет собой разрабатываемый продукт?

Это обёртка над API Keitaro. Функционал обёртки состоит из 2 частей:

1. Создавать кампании

Он должен принимать название кампании, гео-код страны и ID оффера Keitaro и создавать кампанию, которая:

- имеет 2 потока: первый поток ловит всех из указанной страны и редиректит на гугл, второй поток редиректит на выбранный оффер
- имеет настроенные домен, группу и источник (все это тоже есть в API).

2. редактор существующей кампании

В рамках задания редактор работает со списком офферов второго потока кампании:
он умеет добавлять/удалять офферы, восстанавливать удалённые офферы,
запинивать их и публиковать изменения. Изменение характеристик самой кампании
(имени, домена, группы и источника) в объём задания не входит.

Обёртка должна иметь фронт и бэк со своей БД.

Описание архитектуры, в т.ч. структуры БД, см. в _wrk/architecture.md.

### Зачем свой бэк?

Что бэк моей обёртки добавляет к функционалу API Keitaro?

Почему не написать только фронт, работающий с API Keitaro непосредственно?
1. Функционал мягкого удаления потоков из кампании с их визуализацией и возможностью лёгкого восстановления.
2. Хранимые кастомные (запиненые) веса офферов. Они не меняются при дальнейшем редактировании списка офферов 2-го потока кампании.
3. Храним справочник двухбуквенных кодов стран по ISO 3166-1 alpha-2.
4. Проксируем запросы к Keitaro API через свой бэк, чтобы
  - избежать проблемы CORS;
  - решать максимум вопросов бизнес-логики в своём бэке, а не на фронте (фронт максимально глупый. из сообр. безопасности, например).

## 2. Доступный API Keitaro

API доступен на учебном стенде: он отвечает как Admin API трекера Keitaro в той части, что нужна для задания. Пишите обёртку так, будто ходите в настоящий Keitaro. Поля запросов и ответов те же, что в документации Admin API.
Документация Admin API доступна по адресу https://admin-api.docs.keitaro.io/.

Базовый URL API: https://keitaro-for-tests.etolegko.com/admin_api/v1
Ключ доступа я положу в .env.

### Как ходить в тестовый API

```bash
curl -H "Api-Key: <ключ доступа>" https://keitaro-for-tests.etolegko.com/admin_api/v1/offers

# поток «страна → Google»
curl -X POST https://keitaro-for-tests.etolegko.com/admin_api/v1/streams \
  -H "Api-Key: <ключ доступа>" -H "Content-Type: application/json" \
  -d '{"campaign_id": 1, "name": "Geo GM", "type": "regular", "schema": "redirect",
       "action_type": "http", "action_payload": "https://google.com",
       "filters": [{"name": "country", "mode": "accept", "payload": ["GM"]}]}'

# поток с офферами
curl -X POST https://keitaro-for-tests.etolegko.com/admin_api/v1/streams \
  -H "Api-Key: <ключ доступа>" -H "Content-Type: application/json" \
  -d '{"campaign_id": 1, "name": "Офферы", "type": "default", "schema": "landings",
       "offers": [{"offer_id": 18001, "share": 100, "state": "active"}]}'
```

### Что поддержано API учебного стенда из описанного в документации Admin API

| Запрос                                | Объяснение |
| ------------------------------------- | ------------------------------------------------------------------------------ |
| GET /campaigns                        | Ваши кампании, новые сверху. Параметры offset и limit.
| POST /campaigns                       | Создать кампанию. Обязательно name; alias, если не задан, стенд придумает сам.
| GET /campaigns/{id}                   | Одна кампания.
| PUT /campaigns/{id}                   | Изменить кампанию: меняются только присланные поля.
| DELETE /campaigns/{id}                | Удалить кампанию вместе с потоками. Архива нет.
| POST /campaigns/{id}/enable, /disable | Включить, выключить.
| GET /campaigns/{id}/streams           | Потоки кампании по порядку position.
| POST /streams                         | Создать поток. Обязательны campaign_id и name.
| GET /streams/{id}                     | Один поток с фильтрами и офферами.
| PUT /streams/{id}                     | Изменить поток. Поле offers заменяет состав целиком, поле filters — фильтры целиком.
| DELETE /streams/{id}                  | Удалить поток.
| POST /streams/{id}/enable, /disable   | Включить, выключить.
| GET /offers, /offers/{id}             | Офферы. Только чтение.
| GET /groups?type=campaigns            | Группы кампаний. Только чтение.
| GET /domains                          | Домены. Только чтение.
| GET /traffic_sources                  | Источники. Только чтение.

## 3. Описание функционала разрабатываемого продукта


### Справочник кодов стран

Двухбуквенные коды стран по ISO 3166-1 alpha-2 нужно хранить в справочнике этих кодов с именами стран в своей БД. Нужен сидер.

### Список кампаний в UI

#### Поля списка кампаний

Список моих кампаний из своей БД.
Кампании отсортированы по дате создания, новые кампании отображаются сверху.
Список кампаний, в котором видны:
 - id,
 - имя,
 - дата последнего изменения,
 - кнопка удаления.

Группа и источник намеренно не отображаются в списке кампаний. Для ускорения
первоначальной отрисовки списка справочники групп и источников не загружаются
сразу. Они запрашиваются только при открытии формы добавления кампании, где
нужны для выбора значений.

#### Добавление кампании

Наверху кнопка добавления кампании.
Щелчок на кнопке добавления кампании открывает диалог ввода данных новой кампании.
Нужно
 - ввести имя кампании,
 - выбрать домен кампании,
 - выбрать группу,
 - выбрать источник,
 - выбрать двухбуквенный код страны по ISO 3166-1 alpha-2 (поиск по коду и по русскому имени),
 - выбрать оффер для переадресовки из всех стран, кроме указанной.

Домен, группа, источник, оффер выбираются из вариантов, полученных от API запросами GET /domains, GET /groups?type=campaigns, GET /offers.

В наш бэк отправляется 1 post-запрос на создание кампании.
У нас в бэке:
 - отправляется в API учебного стенда запрос на создание кампании:

```
    POST /campaigns
    {
        "name":"<имя-кампании>",
        "type":"position",
        "state":"active",
        "cost_type":"CPC",
        "cost_value":0,
        "cost_currency":"USD",
        "cost_auto":true,
        "group_id":<id-группы>,
        "traffic_source_id":<id-источника>,
        "domain_id":<id-домена>
    }
```
 - Из ответа запоминает id кампании и её alias.
 - Отправляется запрос на создание перехватывающего потока по стране:

```
    POST /streams
    {
        "campaign_id":<id-кампании>,
        "name":"Redirect by country",
        "type":"forced",
        "state":"active",
        "schema":"redirect",
        "action_type":"http",
        "action_payload":"https://google.com",
        "collect_clicks":true,
        "filter_or":false,
        "offer_selection":"before_click",
        "offers":[],
        "filters": [
            {
                "name": "country",
                "mode": "accept",
                "payload": ["<код-страны-по-ISO-3166-1-alpha-2>"]
            }
        ]
    }
```

 - Отправляется запрос на создание обычного потока с офферами:

```
    POST /streams
    {
        "campaign_id":<id-кампании>,
        "name":"with offers",
        "type":"regular",
        "state":"active",
        "schema":"landings",
        "action_type":"http",
        "action_payload":null,
        "collect_clicks":true,
        "filter_or":false,
        "offer_selection":"before_click",
        "filters":[],
        "offers":[
            {
                "offer_id":<id-выбранного-оффера>,
                "share":100,
                "state":"active"
            }
        ]
    }
```

 - Создаём в своей БД записи кампании и офферов её 2-го потока.
   В записи кампании хранится:
    - id кампании
    - имя
    - alias
    - group_id
    - traffic_source_id
    - domain_id
    - id 1-го (перехватывающего) потока,
    - код страны для перехватывающего потока,
    - id 2-го потока,
    - is_dirty = список офферов изменён, но не опубликован в Keitaro.

   Эти действия завёрнуты в транзакцию. При любом сбое посылаем запрос на удаление кампании???

#### Удаление кампании

По нажатии кнопки удаления в строке кампании отправляется запрос DELETE /campaigns/<id-кампании> в наш бэк.
В бэке:
 - Отправляем запрос на удаление кампании в Admin API,
 - удаляем кампанию из нашей БД, а с ней и все записи о её потоках и занятых офферах.

#### Редактирование кампании

По щелчку на имени кампании открывается интерфейс редактирования офферов её 2-го потока.
Видны 2 потока.
Для 1-го из них видно его имя, а также двухбуквенный код страны и её название и упоминание редиректа из этой страны на google. Этот поток никак не редактируется.
Для 2-го из них видно название потока, а ниже список офферов с их названиями и весами. Этот список можно редактировать.

В нашей БД не хранится список потоков кампании. id 1-го и 2-го потоков хранятся в записи кампании.

### Список офферов в UI

Где-то вне списка офферов (например, в строке 2-го потока):
 - кнопка "Запросить офферы потока из Keitaro" активна, когда is_dirty на кампании = false
 - кнопка "Опубликовать офферы потока в Keitaro" активна, когда is_dirty на кампании = true
 - кнопка "Отмена" активна, когда is_dirty на кампании = true
Офферы упорядочены по очерёдности привязки.
В строке каждого оффера:
 - кнопка для запинивания/распинивания
 - кнопка для удаления ИЛИ кнопка для восстановления оффера.
Цвет и начертание текста каждого оффера зависят от его статуса:
 - включён — обычный цвет, регулярное начертание,
 - удалён — бледный цвет, курсивное начертание.
Цвет фона списка офферов зависит от поля is_dirty кампании: false — обычный, true — бледно-жёлтый.
Кнопка запинивания бледная при is_pinned=false, яркая при is_pinned=true, недоступна при is_deleted = true.

Под строками офферов select для выбора оффера из списка свободных. Поиск выполняется, когда введено не менее 2 символов. Запрос с введёнными символами адресуется нашему бэку. Он отсылает запрос GET /offers к Admin API (фильтров и пагинации в этом запросе нет; ответ кэшируется бэком на 10 секунд), затем фильтрует результат по:
 - наличию введённых символов в имени оффера,
 - офферы не должны использоваться в этой же кампании.
 И отправляет ответ фронту.
 Справа от select'а офферов кнопка "Добавить".

В нашей БД для каждого оффера хранится:
 - id,
 - имя,
 - вес,
 - признак, что запинен (is_pinned),
 - признак, что удалён (is_deleted),
 - номер по порядку.

#### Запинивание/распинивание оффера

В нашей БД для указанного оффера признак is_pinned становится соответственно true или false.
Фронту возвращается новый список офферов 2-го потока, фронт его отрисовывает.
Веса назначить вручную нельзя, можно только запинить.

#### Удаление/восстановление оффера

В нашей БД признак is_deleted становится соответственно true или false. Если это удаление, то вес становится 0.

Производится пересчёт весов офферов по алгоритму, указанному в разделе "Алгоритм пересчёта весов офферов для заданной кампании".
Признак is_dirty кампании становится true.

Фронту возвращается новый список офферов 2-го потока, фронт его отрисовывает.

#### Добавление оффера

По нажатии кнопки "Добавить" под списком офферов при наличии выбранного оффера выполняется запрос к нашему бэку с указанием id добавленного оффера.
В нашей БД добавляется строка оффера.

Производится пересчёт весов офферов по алгоритму, указанному в разделе "Алгоритм пересчёта весов офферов для заданной кампании".
Признак is_dirty кампании становится true.

Фронту возвращается новый список офферов 2-го потока, фронт его отрисовывает.

#### Запрос офферов потока из Keitaro

По нажатии кнопки "Запросить офферы потока из Keitaro" специальный запрос отправляется в наш бэк.
В бэке выполняется запрос к API учебного стенда GET /streams/<id-2-го-потока>.

Список офферов в ответе (список A) сверяется с хранящимся в нашей БД:
 - Получаем список офферов потока из нашей БД — список B.
 - Стираем все офферы этого 2-го потока из нашей БД.
 - список офферов для сохранения (список N) инициализируем пустым ([]).
 - Перебираем офферы ответа:
   - находим оффер с таким же id в списке B.
   - заполняем новый оффер данными из оффера из списка A.
   - порядковый номер нового оффера равен позиции оффера из списка A в списке A.
   - is_pinned для нового оффера: если is_pinned у оффера из списка B true и вес точно такой же, как в оффере из списка A, то true, иначе false.
   - добавляем новый оффер к списку N.
   - Если оффер в списке B с таким же id был найден, то удаляем его из списка B.
 - Перебираем офферы, оставшиеся в списке B. Это те, которых нет в ответе, но были в нашей БД.
   - устанавливаем офферу is_deleted = true, вес = 0, is_pinned=false.
   - добавляем оффер к списку N.
 - Список N сохраняем в нашу БД как офферы 2-го потока кампании.

Фронту возвращается новый список офферов 2-го потока, фронт его отрисовывает.

#### Публикация списка офферов в Keitaro

По нажатии кнопки "Опубликовать офферы потока в Keitaro" специальный запрос отправляется в наш бэк.
Бэк выполняет запрос на изменение потока 2 (id берётся из соответствующего поля кампании) с списком офферов из нашей БД с is_deleted = false, см. раздел "Запрос на изменение весов офферов 2-го потока заданной кампании".

#### Отмена изменений офферов

По нажатии кнопки "Отмена" список офферов должен возвращаться к тому виду, каким был после последней публикации в Keitaro.
Решение изложено в файле _wrk/canceling.md.

#### Алгоритм пересчёта весов офферов для заданной кампании
```
Получаем количество офферов заданной кампании, у которых is_deleted = false, is_pinned = false: N
Получаем сумму весов офферов, у которых is_pinned = true: Wp
Wn =  (100 - Wp) // N
Wmax = 100 - Wp * (N - 1)
Далее перебираются все заданной кампании, у которых is_deleted = false, is_pinned = false:
    1-му из них по очерёдности привязки назначается вес Wmax
    остальным — Wn.
Веса офферов с is_deleted = true должны быть 0.
Веса офферов с is_pinned = true не изменятся.
```

#### Запрос на изменение весов офферов 2-го потока заданной кампании
```
PUT streams/<id-2-го-потока>
{
    "filters":[],
    "offers": [
        {
        {"offer_id":<id-оффера>,"share":<новый-вес-оффера>,"state":"active"},
        ...
    ]
}
```
