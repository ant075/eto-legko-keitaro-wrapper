# Архитектура проекта

## Границы системы

Приложение состоит из трёх частей:

1. Vue 3 frontend — отображает данные и вызывает только API нашего backend.
2. FastAPI backend — выполняет бизнес-логику, работает с PostgreSQL и проксирует нужные операции в API учебного стенда.
3. API учебного стенда — внешняя система кампаний, потоков, офферов и справочников.

Frontend не обращается к API учебного стенда напрямую.

## Конфигурация окружения

Backend получает из `.env` следующие настройки:

- `API_KEY` — ключ доступа к API учебного стенда;
- `API_BASE_URL` — базовый URL API учебного стенда;
- `REDIRECT_TARGET_URL` — URL, на который перенаправляет первый поток кампании.

Эти значения не должны быть зашиты в исходный код или передаваться во frontend. Файл `.env` не коммитится в репозиторий; в проекте должен быть шаблон `.env.example` без секретного ключа.

Интеграционный слой backend должен ориентироваться на фактически проверенный контракт учебного стенда из `description.md` и `requests.txt`. В частности, обновление офферов потока выполняется через `PUT /streams/{id}` с полями `filters` и `offers`; поле `offers` заменяет состав офферов целиком.

## Ответственность backend

Backend отвечает за:

- локальное хранение кампаний и их двух потоков;
- справочник стран ISO 3166-1 alpha-2;
- рабочее состояние офферов и снимок последней публикации;
- расчёт весов офферов;
- мягкое удаление и восстановление офферов;
- флаг `is_dirty`;
- создание кампании последовательностью запросов к учебному стенду;
- публикацию рабочего состава офферов в учебный стенд;
- синхронизацию локального состояния с потоком учебного стенда;
- обработку ошибок внешнего API и компенсационное удаление кампании при неудачном создании.

## Модель данных

### `campaigns`

Локальная запись кампании:

- `id` — ID кампании в учебном стенде, первичный ключ;
- `name`;
- `alias`;
- `group_id`;
- `traffic_source_id`;
- `domain_id`;
- `redirect_stream_id` — ID потока, перенаправляющего выбранную страну в Google;
- `offers_stream_id` — ID потока с офферами;
- `country_code` — код страны для redirect-потока;
- `is_dirty` — рабочее состояние офферов отличается от последней публикации;
- `created_at`;
- `updated_at`.

Для сортировки списка кампаний используется индекс `created_at`; кампании
возвращаются по дате создания в обратном хронологическом порядке.

ID кампании является внешним ключом для связанных локальных записей. Удаление локальной кампании должно удалять связанные локальные записи каскадно.

### `campaign_offers`

Рабочее состояние офферов второго потока:

- `campaign_id` — внешний ключ на `campaigns.id`;
- `offer_id` — ID оффера в учебном стенде;
- `name` — локально сохранённое имя оффера;
- `weight`;
- `is_pinned`;
- `is_deleted`;
- `position` — порядок привязки.

Первичный ключ — составной: `(campaign_id, offer_id)`. Для одной кампании `offer_id` уникален. Удаление является мягким: запись сохраняется с `is_deleted = true` и `weight = 0`.

### `campaign_offer_publications`

Снимок последнего опубликованного состояния, используемый кнопкой «Отмена»:

- `campaign_id` — внешний ключ на `campaigns.id`;
- `offer_id`;
- `name`;
- `weight`;
- `is_deleted`;
- `position`;
- `published_at`.

Первичный ключ — составной: `(campaign_id, offer_id)`. Поля `(campaign_id, offer_id)` также образуют внешний ключ на `campaign_offers(campaign_id, offer_id)`.

Снимок не хранит `is_pinned`: это локальная настройка алгоритма, которая не является самостоятельным изменением потока в учебном стенде. При отмене восстанавливаются состав, веса, порядок и статус удаления, а актуальный `is_pinned` сохраняется.

Для каждой кампании существует один актуальный снимок публикации. Его можно реализовать удалением старых строк перед вставкой нового снимка внутри одной транзакции.

### `countries`

Справочник стран:

- `code` — двухбуквенный ISO 3166-1 alpha-2 код;
- `name_ru` — русское название страны.

`code` является первичным или уникальным ключом. Заполнение выполняется сидером.

`campaigns.country_code` — внешний ключ на `countries.code`.

ID групп, источников, доменов, кампаний, потоков и офферов, полученные от учебного стенда, не дублируются внутренними ID. Для кампании и оффера они используются непосредственно как ключи. Потоки не являются отдельными локальными сущностями, поэтому их ID хранятся в `campaigns.redirect_stream_id` и `campaigns.offers_stream_id` без локальных таблиц потоков.

## Состояния офферов

### Рабочее состояние

Хранится в `campaign_offers` и меняется при добавлении, удалении, восстановлении и пересчёте весов.

### Последняя публикация

Хранится в `campaign_offer_publications` и соответствует последнему успешному `PUT /streams/{offers_stream_id}` либо успешной синхронизации с учебным стендом.

### `is_dirty`

- `false` — рабочее состояние совпадает с последней публикацией;
- `true` — есть неподтверждённые изменения состава или весов.

При `is_dirty = true`:

- разрешена публикация;
- разрешена отмена;
- синхронизация из учебного стенда запрещается интерфейсом и backend должен также её отклонять.

## Правила операций

### Добавление, удаление и восстановление

Операции меняют только рабочее состояние PostgreSQL, пересчитывают веса и устанавливают `is_dirty = true`. В учебный стенд запрос не отправляется.

### Pin/unpin

`is_pinned` меняется локально. Само действие:

- не меняет веса;
- не меняет `is_dirty`;
- не отправляет запрос в учебный стенд.

При последующем изменении состава офферов закреплённые веса сохраняются, а незакреплённые пересчитываются.

### Публикация

Backend отправляет в учебный стенд только рабочие офферы с `is_deleted = false`. После успешного ответа заменяет снимок публикации и устанавливает `is_dirty = false`.

### Отмена

Backend заменяет рабочие записи данными снимка последней публикации, устанавливает `is_dirty = false` и не обращается к учебному стенду: он уже содержит последнее опубликованное состояние.

### Синхронизация

Backend получает `GET /streams/{offers_stream_id}`, формирует рабочие записи по правилам из `description.md`, одновременно обновляет снимок публикации и устанавливает `is_dirty = false`.

## Последовательность создания кампании

1. `POST /campaigns` с payload, проверенным в `requests.txt`.
2. `POST /streams` для redirect-потока со страной и Google.
3. `POST /streams` для потока офферов.
4. В одной локальной транзакции сохранить кампанию, два ID потоков, рабочий список офферов и снимок публикации.
5. При сбое внешнего шага после создания кампании выполнить компенсационный `DELETE /campaigns/{id}`.

Локальная транзакция PostgreSQL не может сделать внешние запросы атомарными, поэтому компенсация обязательна; ошибки компенсации должны быть залогированы и возвращены как отдельная диагностическая информация.

## Структура исходников

Планируемая структура проекта:

```text
backend/
  app/
    api/              # HTTP-эндпоинты FastAPI
    core/             # конфигурация и общие исключения
    db/               # engine, Base, session, migrations/seeds
    integrations/     # клиент API учебного стенда
    models/           # SQLAlchemy-модели
    repositories/     # доступ к БД
    schemas/          # Pydantic-схемы
    services/         # бизнес-логика
  tests/
frontend/
  src/
    api/
    components/
    views/
    stores/
    types/
```
